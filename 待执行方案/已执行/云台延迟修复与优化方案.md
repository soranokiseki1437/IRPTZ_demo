## 0. 依据声明

本方案的全部结论来自以下三处可验证来源：

1. 现场运行日志（`build/Desktop_Qt_6_12_0_MinGW_64_bit_Debug/debug/日志/`）；
2. 当前工程源码（以文件行号标注）；
3. 厂家 SDK Demo 源码（`sdk/demo/sdkdemo/`，即厂家上位机 `上位机与客户端/SV_SDK_DEMO_241211` 的配套源码）。

## 1. 结论摘要

**云台"极大延迟"不是视频链路、UI 渲染或云台机械问题，而是网络 SDK 调用通道被测温轮询淹没。**

- 测温轮询频率 1 Hz，每次都用 `QtConcurrent::run` 新起一个线程执行阻塞 SDK 调用，且**没有在途请求保护**；
- 设备侧单次全屏测温约 3 s，请求到达率 1/s、服务率约 0.33/s，队列每秒净积压约 2 s；
- 测温耗时按 3018 → 5043 → 7081 → … → 48425 ms 线性增长，最终顶到 SDK 约 48.4 s 超时上限并持续满负荷；
- 云台运动指令与测温请求走同一设备控制通道，实测单条运动指令阻塞 **30968 ms**；
- 同一 5 s 窗口内，云台角度查询次数从正常的 46 次跌到 3 次，说明 PTZ 线程整段被卡死；
- 阻塞返回的瞬间，早已超时的 500 ms 看门狗立即"补发"急停，现场表现为"按下去半天不动，松手又乱停"。

厂家 Demo 的"成功案例"恰恰是：**测温只在按钮点击时查一次，云台按下发一次、松开发一次，全程没有周期轮询**。我们把厂家按需调用的低频操作改成了 1 Hz 测温 + 10 Hz 角度查询 + 200 ms 重发，超出了 SDK/设备的承受能力。

设测温单次设备处理时间 `S ≈ 3.0 s`，轮询到达间隔 `T = 1.0 s`：

- 队列等待每秒净增 `S - T = 2.0 s`，与日志中每秒 +2 s 完全吻合；

- 此时通道中常驻约 24 条测温请求，PTZ 运动/停止指令只能排在它们后面，30 s 级延迟是必然结果。

| 云台运动 | 按下发一次，松开发一次（`sdkdemo.cpp:1404-1440`、`8574-8583`） | 另加 200 ms 重发 + 500 ms 看门狗 | 事件队列堆积、误急停 |

**可直接借鉴的三条原则：**

1. 测温、云台角度这类"辅助信息"不做高频自动轮询，按需或低频查询；
2. 同一 `userID` 的阻塞 SDK 调用必须串行、可控，禁止无上限并发；
3. 云台运动只依赖"按下/松开"两条指令，设备的运动状态由设备自己保持，不需要上位机高频重发。

## 4. 根因分解

### 4.1 主因：测温轮询无背压

`requestGlobalMaxMinTemp()` 每被调用一次就投递一个并发任务。只要上一次没返回，下一次照样投递。设备处理不过来时，任务在 SDK/设备队列中无限堆积，形成"雪崩"：

```
t=0s   测温#1 开始，3s 完成
t=1s   测温#2 排到 #1 后面
t=2s   测温#3 排到 #2 后面
...
t=24s  等待时间达到 48s，此后每条都顶到 SDK 超时
```

积压期间，云台运动指令进入同一队列，延迟随积压深度线性增长。

### 4.2 次因：PTZ 线程与阻塞调用强耦合

`NetPtzController` 整个对象运行在一个 QThread 上（`mainwindow.cpp:829-870`），运动、停止、角度查询全部串行执行。任意一次 SDK 调用阻塞，后续所有指令（包括"松开停止"）都被推迟。看门狗定时器也运行在同一个线程，无法在阻塞期间触发。

### 4.3 时序缺陷：看门狗启动位置错误

`moveDirection()` 在调用阻塞 SDK **之前**执行 `m_stopWatchdog->start(500)`。线程被阻塞 30 s 期间，500 ms 超时事件早已到期；一旦 SDK 返回、事件循环恢复，该超时立即执行，导致：

- 用户还按着方向键，云台却被急停；
- 阻塞期间积压的 200 ms 重发事件与新状态交错，产生顿挫。

### 4.4 其它已确认隐患

| 隐患 | 位置 | 说明 |
|---|---|---|
| UI 线程同步 SDK 调用 | `mainwindow.cpp:1326`（伪彩）、`1308`/`1319`（FFC） | 当前测温积压时，点一次伪彩/校准会冻结界面数十秒 |
| 抓图阻塞 UI | `capturemanager.cpp:75-120`，由 `mainwindow.cpp:676` 直接调用 | `SV_NET_DEV_CaptureJPEGPicture_V13` 是阻塞网络调用 |
| 登录阻塞 UI | `devicemanager.cpp:66-88` | 实测登录约 2.9 s（日志 11:48:29.869 → 11:48:32.752） |
| 录像结束停止角度轮询 | `mainwindow.cpp:792-796` | 停止录像后角度反馈永久消失，只能重连恢复 |
| PTZ 线程并发来源 | 全局线程池 `QtConcurrent` | 测温线程与抓图后处理共用全局池，极端情况下互相拖累 |

## 5. 修复方案

### P0（必须，先解决云台延迟）

#### P0-1 测温查询改造：单飞 + 降频 + 操作期暂停

**文件**：`infraredservice.h`、`infraredservice.cpp`、`mainwindow.cpp`

1. `InfraredService` 增加在途标志：

```cpp
// infraredservice.h
#include <atomic>
...
private:
    std::atomic<bool> m_tempQueryInFlight{false};
```

2. `requestGlobalMaxMinTemp()` 改为单飞，在途时直接丢弃本次轮询：

```cpp
void InfraredService::requestGlobalMaxMinTemp()
{
    if (!m_session || !m_session->isLoggedIn()) return;

    // 单飞：上一请求未返回时不再投递，杜绝队列堆叠
    bool expected = false;
    if (!m_tempQueryInFlight.compare_exchange_strong(expected, true)) {
        return;
    }

    const LONG uid = m_session->userId();
    QPointer<InfraredService> guard(this);
    QtConcurrent::run([guard, uid]() {
        QElapsedTimer t;
        t.start();
        float retTemp[4] = {0.0f};
        const LONG ret = SV_NET_DEV_GetThmlMtFSMaxMinVal(uid, retTemp);
        const qint64 costMs = t.elapsed();

        if (!guard) return;                 // 服务已销毁，标志无意义
        guard->m_tempQueryInFlight.store(false);  // 所有返回路径都要复位

        if (ret == 0) emit guard->globalTempUpdated(retTemp[0], retTemp[1]);
        if (costMs > 500)
            qWarning() << "[InfraredService] 测温单次耗时:" << costMs << "ms";
    });
}
```

3. 轮询间隔从 1000 ms 改为 **5000 ms**（`mainwindow.cpp:878`）：

```cpp
m_tempPollTimer->start(5000);
```

4. 手动操作云台期间暂停测温（`mainwindow.cpp:615-629`）：

```cpp
void MainWindow::startManualMove(...)
{
    ...
    m_tempPollTimer->stop();          // 运动期间让出控制通道
    emit ptzMoveDirection(...);
    m_ptzManualRepeatTimer->start();
}

void MainWindow::stopManualMove()
{
    m_ptzManualRepeatTimer->stop();
    emit ptzStop();
    if (m_rgbConnected) m_tempPollTimer->start(5000);  // 松开后恢复
}
```

**预期效果**：

- 测温通道占用从"无限积压"降为"至多 1 条在途"；
- 手动云台操作期间测温请求为 0；
- 日志中 `测温 SDK 调用耗时过长` 不再逐秒增长，稳定在单次约 3 s。

#### P0-2 角度查询降频，运动期间跳过

**文件**：`netptzcontroller.cpp`、`mainwindow.cpp`

1. `queryAngle()` 增加运动态判断：

```cpp
void NetPtzController::queryAngle()
{
    if (!isOpen() || !m_angleSupported) return;
    if (m_isMoving) return;   // 运动期间不占用控制通道，由下一 tick 自动恢复

    ...
}
```

2. 默认轮询间隔 100 ms → **200 ms**（5 Hz）：

```cpp
// mainwindow.cpp:874
emit ptzStartAutoQuery(200);
```

3. 录像开始时如需 10 Hz，可保持 100 ms；录像结束时恢复 200 ms 而不是停止查询：

```cpp
// mainwindow.cpp:792-796 改为
if (m_ptzController) emit ptzStartAutoQuery(200);   // 恢复空闲频率
```

**预期效果**：SDK 每秒调用次数从约 11 次降到约 5 次；运动期间 PTZ 线程只处理运动/停止，不再被查询插队。

#### P0-3 看门狗时序修正

**文件**：`netptzcontroller.cpp:119-142`

1. 进入 `moveDirection()` 时刷新看门狗（保留原有的按压保活语义）；
2. **阻塞调用返回后重新计时**，避免超时事件"补发"：

```cpp
m_stopWatchdog->start(500);          // 按压保活计时
...
sendSdkPtz(dwCommand, 0, dwSpeed);
...
m_stopWatchdog->start(500);          // 关键：从真正返回时刻重新计时
```

3. 看门狗日志补充上下文，便于现场判断：

```cpp
qWarning() << "[NetPtzController] 500ms 未收到后续运动指令，自动急停"
           << " lastCmd =" << m_lastCmd
           << " moving =" << m_isMoving;
```

**预期效果**：不再出现"SDK 刚返回就误急停"。

#### P0-4 删除或收敛周期性重发

**文件**：`mainwindow.cpp:115-118`

厂家 Demo 只发一次运动命令即可持续转动（`sdkdemo.cpp:1404-1440`）。当前重发的作用仅是刷新看门狗，命中方向/速度去重后并不会真正调用 SDK（`netptzcontroller.cpp:127-129`），但会在 SDK 阻塞时堆积大量事件。

建议：

- 保留 200 ms 重发作为"按压保活"可以接受，但**必须配合 P0-1、P0-3**；
- 若现场希望进一步简化，可改为：按下发一次 + 松开发一次 + 窗口失焦/关闭时补发停止（见 P1-4）。

### P1（本轮应做，消除其它卡顿源）

#### P1-1 引入统一 SDK 串行调度器（推荐的核心架构）

**新增**：`sdkdispatcher.h/.cpp`（约 150 行）

厂家 Demo 的隐含前提是"SDK 调用低频且串行"。我们程序有 4 个并发来源（PTZ 线程、UI 线程、QtConcurrent、Lens 线程），应显式收口：

```cpp
class SdkDispatcher : public QObject {
    Q_OBJECT
public:
    enum Priority { PtzStop = 0, PtzMove = 1, Lens = 2, Capture = 3,
                    Config = 4, AngleQuery = 5, TempQuery = 6 };
    void post(Priority p, std::function<void()> fn);
private:
    // 单工作线程 + 优先级队列 + 合并规则：
    // - PtzStop 不可丢弃，最高优先级
    // - PtzMove 只保留最新一条
    // - AngleQuery / TempQuery 在途时不再入队
};
```

要点：

- 所有 `SV_NET_DEV_*` 调用只允许在该线程执行；
- 云台停止指令永远优先于其它排队请求；
- 测温、角度查询使用"最新值合并 + 单飞"；
- 各业务对象通过信号/回调取结果，不直接碰 SDK。

该改造可彻底消除"某条慢调用拖死云台"的问题，也是后续加功能（预置位、镜头、抓图）的安全基础。

#### P1-2 UI 线程阻塞 SDK 调用迁移

| 功能 | 现状 | 改法 |
|---|---|---|
| 伪彩切换 `setPalette` | UI 线程同步（`mainwindow.cpp:1326`） | 投递到 SdkDispatcher；切换期间禁用下拉框，结果回来再恢复 |
| 快门/背景 FFC | UI 线程同步（`mainwindow.cpp:1308`、`1319`） | 投递到 SdkDispatcher；按钮置灰防重复点击 |
| 抓图 `captureOnce` | UI 线程同步（`mainwindow.cpp:676`） | 抓图调用移到 SdkDispatcher；保存仍走现有 QtConcurrent |
| 登录 | UI 线程同步约 3 s（`devicemanager.cpp:66-88`） | 保持同步实现，但放入后台任务并显示"连接中"，避免界面假死 |

#### P1-3 测温 OSD 按需化

**文件**：`mainwindow.cpp`、`mainwindow.ui`、`configmanager.*`

- 增加"显示全局温度"复选框，默认关闭；
- 关闭时不启动 `m_tempPollTimer`，SDK 测温调用为 0；
- 开启时按 5 s 轮询，并受 P0-1 单飞保护；
- 配置项持久化，避免每次启动都开启。

这与厂家 Demo 的"按需查询"一致，是现场最稳妥的默认行为。

#### P1-4 云台停止的兜底触发

**文件**：`mainwindow.cpp`

除松开按钮外，补充以下停止触发点：

- 主窗口 `deactivate` / 失去焦点；
- 关闭窗口、断开连接；
- 跟踪启动/停止切换瞬间。

目的：避免"按下后窗口失焦，released 事件收不到"导致云台持续转动。厂家 Demo 无此保护，我们应补上。

### P2（性能与可观测性优化）

#### P2-1 视频显示链路

现状已做较好（`mainwindow.cpp:450-505`）：浅拷贝帧、先缩放再转 QPixmap、FastTransformation、日志节流。剩余小项：

- 温度 OSD 打开时，每帧都会因 `QPainter` 触发 pixmap 深拷贝；可将温度文本缓存为 1 s 更新一次的预绘制层，避免每帧复制；
- 叠加内容无变化时直接复用上一帧 pixmap（当前已部分实现）。

#### P2-2 日志与指标

- `NetPtzController` 的 5 s 统计增加 p95 与失败次数；
- 测温日志改为"成本 > 500 ms 才记录"，并输出在途标志，便于确认单飞生效；
- 保留现有 UI 心跳探测（`mainwindow.cpp:44-59`），作为验收指标之一；
- 首包 `avcodec_send_packet` 失败（日志第 12-13 行）是 RTSP 首包正常现象，后续解码成功，不需要处理。

#### P2-3 线程优先级

- PTZ 线程可尝试 `QThread::HighPriority`，降低被系统调度挤压的概率；
- 但优先级不能替代 P1-1，SDK 串行化才是根本。

## 8. 风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| 测温降频到 5 s | OSD 温度刷新变慢 | 温度变化本身缓慢，可接受；P1-3 提供开关 |
| 运动期间不测温 | OSD 冻结数秒 | 与厂家的按需查询一致 |
| 单飞丢弃轮询 | 偶发少一帧温度 | 无业务影响 |
| 改角度轮询频率 | 录像 CSV 角度采样变稀 | 录像期间保持 100 ms，非录像 200 ms |
| P1-1 架构改造 | 改动面大 | 独立分支/独立提交；P0 先行验证 |

回滚方式：P0 改动集中在 3 个文件、约 30 行，可直接 `git revert` 对应提交恢复。
